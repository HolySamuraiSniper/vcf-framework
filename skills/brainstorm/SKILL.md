# /vcf-framework:brainstorm — Step 02: Vague idea → design doc

**Goal:** Convert "I want a thing that does X" into a written artifact you can argue with.

This is Step 02 of 10 in VCF gate mode. For full doctrine, see `vcf-framework:overview`.

## Argument

Takes one argument: `<feature-slug>` (must match an existing `.vcf/<slug>/` directory from `/vcf-framework:context`).

## Prereqs

- `<cwd>/.vcf/<feature-slug>/CONTEXT.md` must exist (output of `/vcf-framework:context`).
- `<cwd>/.vcf/<feature-slug>/STATUS.md` must exist.

If either is missing, **halt** and tell the user: "Missing `CONTEXT.md` for `<feature-slug>`. Run `/clear` then `/vcf-framework:context <feature-slug>` first." Do not proceed.

## Inputs to read

- `<cwd>/.vcf/<feature-slug>/CONTEXT.md` — the 3 things + assumptions + relevant prior decisions
- `<cwd>/.vcf/<feature-slug>/IDEATION.md` if it exists — goals, constraints, risks, hard-to-falsify assumptions from `/vcf-framework:office-hours`. Ground the alternatives in these.
- `<cwd>/.vcf/<feature-slug>/STATUS.md` — verify the loop state
- Project `CLAUDE.md` / `AGENTS.md` if not already cached — for hard constraints

## Process

Invoke `superpowers:brainstorming` for the structured exploration of the solution space. The deliverable is a `design.md` capturing alternatives, tradeoffs, and the chosen path.

Anchor the brainstorm in the unverified assumptions from `CONTEXT.md` — surface those during the exploration, don't leave them silent.

## Output

Write `<cwd>/.vcf/<feature-slug>/design.md`:

```markdown
# Design: <feature-slug>

Generated by /vcf-framework:brainstorm at <ISO timestamp>.

## Problem (in user's words, not paraphrased)

> "<verbatim quote from the user, or the closest available phrasing from CONTEXT.md>"

## Alternative shapes considered

### Option A: <name>

- **How it works:** <one paragraph>
- **What we gain:** <bullets>
- **What we give up:** <bullets — be specific, this is the tradeoff>

### Option B: <name>

- **How it works:** ...
- **What we gain:** ...
- **What we give up:** ...

### Option C: <name>

- **How it works:** ...
- **What we gain:** ...
- **What we give up:** ...

## Picked: Option <letter>

**Why this one and not the others:** <2-3 sentences naming the decisive factor>

**What we're explicitly giving up by picking this:** <one bullet per tradeoff>

## Hard constraints

- **Performance budget:** <e.g. p95 < 200ms>
- **Compatibility:** <e.g. must work on Node 18+>
- **Security boundary:** <e.g. all input from /api/* validated via Zod>
- **Other:** <project-specific constraints from CLAUDE.md / AGENTS.md>

## What this is NOT

- <thing it looks related to but isn't>
- <thing the user might assume but we're explicitly not building>
```

## Discipline

A design doc you can't show another engineer is not a design doc. If the genuine answer fits in one paragraph, write the paragraph and skip to `/vcf-framework:prd` — don't pad volume to look thorough.

The **"What we give up"** lines under each option are load-bearing. If they're empty or vague, you haven't actually compared the options — you've listed them. Force concrete tradeoffs.

## After this step

1. Append to `STATUS.md`:
   - `- 02 complete at <timestamp> → see design.md`
   - Update `**Current step:**` to `03 — /vcf-framework:prd`
   - Update `**Last completed:**` to `02`
2. Tell the user verbatim: "Step 02 (brainstorm) complete for `<feature-slug>`. Run `/clear` then `/vcf-framework:prd <feature-slug>` to lock scope."
