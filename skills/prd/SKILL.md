# /vcf-framework:prd — Step 03: Design doc → product requirements

**Goal:** Lock scope and acceptance criteria before architecture. Skipping this is where features creep and "done" becomes negotiable.

This is Step 03 of 10 in VCF gate mode. For full doctrine, see `vcf-framework:overview`.

## Argument

Takes one argument: `<feature-slug>`.

## Prereqs

- `<cwd>/.vcf/<feature-slug>/design.md` must exist (output of `/vcf-framework:brainstorm`).

If missing, **halt** and tell the user: "Missing `design.md` for `<feature-slug>`. Run `/clear` then `/vcf-framework:brainstorm <feature-slug>` first." Do not proceed.

## Inputs to read

- `<cwd>/.vcf/<feature-slug>/design.md` — the chosen shape and hard constraints
- `<cwd>/.vcf/<feature-slug>/CONTEXT.md` — for unverified assumptions and prior decisions
- `<cwd>/.vcf/<feature-slug>/STATUS.md` — verify loop state and tier

## Process

If the project has a `to-prd` skill (e.g., Joey does), invoke it. Otherwise generate the PRD directly using the template below.

The **acceptance criteria** become red tests in `/vcf-framework:build`. Each must be:

- **Concrete** — references specific states, actions, observable outcomes
- **Falsifiable** — pass/fail is unambiguous
- **Independent of implementation** — describes behavior, not code structure

The **out-of-scope** list is more important than the in-scope list. It's what prevents drift mid-build. If you can't list 3+ things explicitly out of scope, you haven't thought hard enough about what you're not doing.

## Output

Write `<cwd>/.vcf/<feature-slug>/PRD.md`:

```markdown
# PRD: <feature-slug>

Generated by /vcf-framework:prd at <ISO timestamp>.

## User stories

### Story 1: <one-sentence summary>

- **As a** <role>
- **I want** <goal>
- **So that** <reason>
- **Happy path:** <what success looks like>
- **Edge case:** <one specific edge case worth naming>

### Story 2: ...

## Acceptance criteria

Each criterion becomes a red test in /vcf-framework:build. Falsifiable, behavior-focused, implementation-agnostic.

- [ ] Given <initial state>, when <action>, then <observable outcome>.
- [ ] Given <initial state>, when <action>, then <observable outcome>.
- [ ] ...

## Scope

### IN (what we ARE building)

- ...
- ...

### OUT (what we are explicitly NOT building — more important than IN)

- ...
- ...
- ...

## Success metrics

- **Production signal:** <what tells us this worked in the real world, measurable>
- **Anti-signal:** <what would tell us it didn't, measurable>
- **Time horizon:** <when we'd judge this — e.g. 30 days post-ship>

## Non-goals

- <thing that looks related but isn't this work>
- <thing reviewers will ask "why didn't you also do X" about — name it>

## Open issues for /vcf-framework:plan

- <anything that needs to be resolved in planning but doesn't belong in PRD>
```

## Discipline

If working with a stakeholder, this is the alignment checkpoint — get explicit sign-off before plan.

If working solo, write it anyway — future-you is the stakeholder, and future-you will ship the wrong thing if "we'll figure out acceptance during build" survives this gate.

## Alternative entry path

If no `design.md` exists (rare path — `:brainstorm` was skipped because the design fell out of the conversation), an alternative is Pocock's `to-prd` skill — synthesize PRD directly from the chat conversation. Install separately if not already present. Output still lands in `<cwd>/.vcf/<feature-slug>/PRD.md` so downstream gates work.

## After this step

1. Append to `STATUS.md`:
   - `- 03 complete at <timestamp> → see PRD.md`
   - Update `**Current step:**` to `04 — /vcf-framework:plan`
   - Update `**Last completed:**` to `03`
2. Tell the user verbatim: "Step 03 (PRD) complete for `<feature-slug>`. Run `/clear` then `/vcf-framework:plan <feature-slug>` for the technical architecture."
