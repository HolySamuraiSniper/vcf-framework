# /vcf-framework:map-codebase — Architectural overview

**Goal:** When `/vcf-framework:context` needs more than module-level understanding of an unfamiliar codebase, this skill builds a subsystem-level map.

`zoom-out` answers "what calls this module?" — `map-codebase` answers "what subsystems exist and how do they relate?".

## Argument

Takes one argument: `<feature-slug>`. If no `.vcf/<feature-slug>/` exists, route to `/vcf-framework:context` first to bootstrap.

## Prereqs

- `<cwd>/.vcf/<feature-slug>/` must exist (bootstrap from `/vcf-framework:context`).

## Inputs to read

- Project `CLAUDE.md`, `AGENTS.md`, `CONTEXT.md`, `docs/glossary.md` — domain vocabulary
- `docs/adr/` — architectural decisions
- Top-level directory listing of `src/` (or equivalent)
- `package.json` / `pyproject.toml` / etc. — what runs and what depends on what
- The repo's main entrypoints (typically `app/`, `pages/`, `cmd/`, `main.*`, or whatever the framework convention dictates)

Spawn a sub-`Agent` with `subagent_type: "Explore"` if the codebase is large — let it map the structure in parallel, return summaries.

## Process

1. Identify subsystems — clusters of related code that share a responsibility. Use the project's domain vocabulary where it has names (`CONTEXT.md` is authoritative).
2. For each subsystem, identify:
   - **What it owns** (data + behavior, in domain terms)
   - **Public surface** (what other subsystems can call into it)
   - **Dependencies** (which other subsystems / external services it calls)
   - **Where it lives** (path)
3. Note cross-cutting concerns that don't fit a single subsystem (auth, logging, schema migrations, etc.).
4. Note dead zones — directories that look important but seem unused. Flag for `improve-codebase-architecture`.

## Output

Write `<cwd>/.vcf/<feature-slug>/CODEBASE-MAP.md`:

```markdown
# Codebase Map: <feature-slug>

Generated by /vcf-framework:map-codebase at <ISO timestamp>.

## Subsystems

### <Subsystem name (domain term from CONTEXT.md)>

- **Owns:** <data + behavior>
- **Public surface:** <interfaces other subsystems call>
- **Depends on:** <other subsystems + external services>
- **Lives at:** `<path>`

### <Next subsystem...>

...

## Cross-cutting concerns

- **Auth:** `<path>` — <one-line summary>
- **Logging / observability:** `<path>` — <one-line summary>
- **Schema migrations:** `<path>` — <one-line summary>
- ...

## Dead zones (flagged for future investigation)

- `<path>` — <why it looks unused>

## Entry points

- `<command / route / process>` → `<path>` (where execution starts)
- ...

## Where the feature-slug work probably lives

For `<feature-slug>` (per CONTEXT.md), likely touches: <list of subsystems + paths>
```

## After this step

1. Append to STATUS.md: `- map-codebase complete at <timestamp> → see CODEBASE-MAP.md`.
2. Tell the user: "Codebase map written for `<feature-slug>`. Resume the loop — next step depends on where you are in STATUS.md. Likely `/clear` then `/vcf-framework:brainstorm <feature-slug>` if `:context` is the only prior step."

## Discipline

This is read-only. Do not modify source code while mapping. If you find genuine bugs or architectural issues, note them in CODEBASE-MAP.md's "Dead zones" or as open issues — don't fix them here.

For codebases small enough that `zoom-out` answers the question, skip this skill. Don't produce a map when a one-line answer suffices.
