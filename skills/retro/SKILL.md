# /vcf-framework:retro — Retrospective ritual

**Goal:** A structured retro before closeout that captures the lessons worth compounding.

`/vcf-framework:closeout` already includes memory write-back, but the retro skill makes it a **named ritual** with a specific format so the lessons aren't skipped under time pressure.

## Argument

Takes one argument: `<feature-slug>`.

## Prereqs

- `<cwd>/.vcf/<feature-slug>/FINAL-REVIEW.md` and `VERIFY.md` must exist (output of `/vcf-framework:final-audit`).

If missing, halt and route to `/vcf-framework:final-audit`.

## Inputs to read

- All `.vcf/<feature-slug>/*.md` artifacts — the loop's whole story
- `git log` since the loop started — what actually shipped
- `<cwd>/.vcf/<feature-slug>/SELF-EVAL.md` if it exists — your honest assessment vs the PRD

## Process

Walk through these prompts. Answer each with concrete examples from this loop, not platitudes:

### 1. Surprises

What turned out different than expected? Examples that count:

- A library/API behaved differently than you assumed
- A test caught something at slice 2 that you'd have caught earlier with a different `:plan`
- A reviewer (slice-audit or final-audit) found something the build agent missed
- An assumption from `:context` that turned out wrong

### 2. Decisions worth remembering (with why)

Which decisions in this loop should compound into future loops? Examples:

- "Used X library because Y — would do again"
- "Picked Tier 4 because the slices were independent — saved 2 hours"
- "Skipped grill-with-docs because the design was obvious — was right, no rework"

The **why** matters more than the decision. A bullet without the why won't help future-you.

### 3. Gotchas for next loop

What would have helped at `/vcf-framework:context` of this loop? Future loops in this area should pick this up:

- "X module has a hidden FK constraint on Y — caught it in slice 3 audit, easier next time if surfaced at :context"
- "The test harness for Z needs a separate fixture — non-obvious"

### 4. New invariants or conventions established

What rules did this loop add to the codebase? Examples:

- "Every X type now must have a Y guard — new convention, no exceptions"
- "Z module owns the W contract; callers don't compose it themselves"

### 5. Slice-audit calibration

This is the **meta-feedback** for the framework itself. If `/vcf-framework:final-audit` caught issues that `/vcf-framework:slice-audit` (per-slice) missed, name the **type** of issue:

- Pattern: <what kind of bug>
- Why per-slice audit missed it: <reason>
- What would have caught it: <reviewer change, scope change, additional check>

Skipping this means the framework stops improving.

## Output

Append (or write if missing) sections to `<cwd>/.vcf/<feature-slug>/CLOSEOUT.md`:

```markdown
## Retro

Generated by /vcf-framework:retro at <ISO timestamp>.

### Surprises
- ...

### Decisions worth remembering
- <decision> — <why>

### Gotchas for next loop
- ...

### New invariants / conventions
- ...

### Slice-audit calibration
- **Pattern:** ...
- **Why per-slice missed it:** ...
- **What would have caught it:** ...
```

## After this step

1. Append to STATUS.md: `- retro complete at <timestamp> → see CLOSEOUT.md retro section`.
2. Tell the user verbatim: "Retro captured for `<feature-slug>`. Run `/clear` then `/vcf-framework:closeout <feature-slug>` to finish the loop."

If `:closeout` was already run, this retro becomes an addendum — STATUS.md gets a new entry but the loop is otherwise unchanged.
