# /vcf-framework:context — Step 01: Ground the work

**Goal:** Before any idea, surface what already exists. Most rework is a context failure.

This is Step 01 of 10 in VCF gate mode. For the full doctrine, tier system, and Joey playbook, see `vcf-framework:overview`.

## Argument

Takes one argument: `<feature-slug>` in kebab-case (e.g. `appointments-sync`, `materials-intel`, `provider-codegen`). If the user didn't provide one, ask via AskUserQuestion before proceeding — slugs are load-bearing because they name the state directory.

## Bootstrap

On first invocation for a `<feature-slug>`:

1. If `<cwd>/.vcf/` doesn't exist, create it.
2. Create `<cwd>/.vcf/<feature-slug>/`.
3. Initialize `<cwd>/.vcf/<feature-slug>/STATUS.md` with this template:

```markdown
# VCF Status: <feature-slug>

- **Started:** <ISO timestamp>
- **Tier:** UNSET — set this manually based on `vcf-framework:overview` tier table
- **Current step:** 01 — /vcf-framework:context
- **Last completed:** none

## Step log

- 01 in progress at <timestamp>
```

If `STATUS.md` already exists, this is a re-run — read it, note the existing state, and append `01 re-run at <timestamp>` to the step log. Don't overwrite.

## Inputs to read

Do these in parallel where independent:

- Persistent memory: `claude-mem:mem-search` if available, otherwise scan `~/.claude/projects/*/memory/MEMORY.md` and topic files for prior related decisions
- `git log --oneline -30` and `git log --all --oneline -50 -- <relevant-paths>` to see recent direction
- `git blame` on files likely to be touched — the *why* lives in commit messages
- Project `CLAUDE.md`, `AGENTS.md`, repo conventions doc, glossary
- If the codebase is unfamiliar: `claude-mem:smart-explore` or grep + read of obvious entry points to map territory

## Output

Write `<cwd>/.vcf/<feature-slug>/CONTEXT.md`:

```markdown
# Context: <feature-slug>

Generated by /vcf-framework:context at <ISO timestamp>.

## Three things that change my approach

1. <something specific from memory / git / code — concrete, falsifiable>
2. <something specific>
3. <something specific>

## Unverified assumptions I'm carrying

- <assumption> — verify by <how>
- <assumption> — verify by <how>

## Relevant prior decisions

- [Link to ADR / decision doc / commit / memory entry]: <one-line summary>
- ...

## Files I'll likely touch

- `path/to/file` — <why>
- `path/to/file` — <why>

## Open questions for the user (if any)

- <question that genuinely blocks brainstorm>
```

## Discipline

If you can't list three things that change your approach, **you didn't look hard enough**. Halt and look again. This is the bedrock of every loop — skipping it cascades into PRD-rewriting later.

Don't fabricate the three things. If genuinely nothing in memory or git changes the approach, that's signal — either this is a real green field (rare) or you didn't dig deep enough (more common). Probe further before committing to "nothing relevant".

## After this step

1. Append to `STATUS.md`:
   - `- 01 complete at <timestamp> → see CONTEXT.md`
   - Update `**Current step:**` line to `02 — /vcf-framework:brainstorm`
   - Update `**Last completed:**` line to `01`
2. Tell the user verbatim: "Step 01 (context) complete for `<feature-slug>`. Run `/clear` then `/vcf-framework:brainstorm <feature-slug>` to continue."

The `/clear` instruction is load-bearing — it's what gives the next step a fresh context window.
